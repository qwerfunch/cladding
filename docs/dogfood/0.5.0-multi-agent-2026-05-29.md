## Bugs found

### Bug #1 — `META_INTEGRITY` detector false-positive on external projects (P0) ✅ FIXED

**Severity**: high — fires on every `clad check` against a user project, blocking the drift gate.

**Repro (pre-fix)**:
```
$ cd /tmp/dogfood-cladding
$ clad check    # or: complete_work({featureId})
✗ Drift
    [META_INTEGRITY] — spec/schema.json unreadable or invalid JSON:
      ENOENT: no such file or directory, open 'src/spec/schema.json'
```

**Root cause**: `src/stages/detectors/meta-integrity.ts:34` hard-coded `join(cwd, 'src', 'spec', 'schema.json')`. That path only exists inside cladding's own repo (where the JSON Schema is checked in). External users get the schema via the cladding npm package's `dist/`, not via their own project's `src/`.

**Fix**: Skip silently when `cwd/src/spec/schema.json` is absent. META_INTEGRITY is a maintainer self-check; it has no signal for external users.

**Patch landed**: yes — `src/stages/detectors/meta-integrity.ts` + `tests/stages/meta-integrity.test.ts`. Full regression: 1165/1165.

### Bug #2 — `completeWork` doesn't roll back active-work registry on partial-fail (moderate) ⏳ logged

**Severity**: medium — work transactions can be left "stuck open" in `.cladding/work-registry.json` when `appendEvidence` throws partway through the evidence loop.

**Repro**:
```ts
completeWork({
  featureId,
  evidence: [{acId: 'nonexistent-AC', ref: 'src/x.ts'}],
});
// throws "no acceptance_criterion with id nonexistent-AC"
// → spec status: still in_progress
// → .cladding/work-registry.json: still active
// → no work_completed event emitted
// → caller must call abandonWork() to recover
```

**Recommendation**: wrap the evidence loop in try/catch. On partial failure either (a) roll back the prior successful appendEvidence calls + abandon the work, or (b) emit a `work_completed_partial` event so audit can flag the state.

**Patch**: not landed (design discussion needed — choose roll-back vs partial-event-emit). Logged as separate ticket.

### Bug #3 — AC ID format inconsistency between `appendEvidence` and `loadSpec` (low) ⏳ logged

**Severity**: low — UX paper cut, not a correctness issue.

**Repro**:
```ts
// Step 1: write AC with id 'AC-1' (not 'AC-001')
// Step 2: appendEvidence(cwd, featureId, 'AC-1', 'src/x.ts')  ← succeeds
// Step 3: executeDrive() → loadSpec()
//   throws "instance.features[0].acceptance_criteria[0].id: does not match pattern ^AC-\\d{3,}$"
```

`appendEvidence` doesn't validate the AC id format; it only checks for exact-string match against existing AC ids on the shard. Meanwhile `loadSpec` runs full schema validation, which enforces `^AC-\d{3,}$` (3+ digits — `AC-001` minimum).

**Recommendation**: either (a) `appendEvidence` rejects AC ids that don't match the schema pattern (defensive, fail fast), or (b) relax the schema to `^AC-\d{1,}$` (allow `AC-1` for simple specs). Option (a) is preferred — matches "fail at write" convention.

**Patch**: not landed. Logged.

### Limitation L1 — LLM unavailable during sandbox dogfood (not a bug)

`clad init <intent>` falls back to deterministic mode without an LLM dispatcher connected. The onboarding Q&A loop is skipped (`status: done` immediately, empty `qa: []`). `docs/project-context.md` quotes the intent verbatim instead of LLM-refined content. This is documented behavior, not a bug — but worth noting that the full dogfood is degraded without LLM access.

## Summary

The cladding 0.5.0 flow works end-to-end. 13 of 13 expected behaviors verified. One real bug surfaced and patched (META_INTEGRITY false-positive). Two design-discussion issues logged for separate tickets. The audit trail + dispatch hint + capability envelope + dispatch_drift detection (PR-A.3 + PR-B) all do what the architecture doc promised.

What the dogfood could *not* exercise (sandbox limitations):

- LLM-driven onboarding refinement (no LLM dispatcher connected) — L1 above
- Real toolchain gates (no tsconfig / no ESLint in /tmp project) — `type`/`lint` correctly skip
- Live MCP tool surface (Claude Code's MCP client is connected to the installed `clad@0.4.0`, not the in-tree 0.5.0 build) — bypassed via direct module imports in the harness
