# v0.4.0 Consistency Benchmark — cladding-on vs vibe coding

> Compressed abstract — 2026-07-05, 0.8.1 cleanup. Original measured 2026-05-28 against the cladding v0.4.0 release.

Six-phase benchmark on an isolated `/tmp/clad-bench/` workspace (install → init-scenario matrix → 7-trap gauntlet → consistency thesis → 5-iteration dev cycle → cladding-on vs cladding-off), 12 host-AI calls across Claude Code and Gemini CLI, no API keys set (cladding's internal LLM dispatcher fell to deterministic fallback; the host AIs used their own credentials for the slash-command path).

Headline numbers:
- Consistency: **60.3%** more consistent cladding-on vs cladding-off on the same HMAC-SHA256 webhook-validation task run twice (Δ 443 → 176 lines) — high confidence, with the caveat below.
- **52%** LOC reduction (282 → 135 avg); **100%** intentional-drift detection (2/2) in the dev cycle; **71%** trap detection (5/7 = 4 clean + 1 schema-time); **0** diff across 4 same-input deterministic-CLI runs; **79**-line Gemini same-prompt non-determinism cladding cannot suppress.

Headline caveat (author's own wording): the 60% consistency gain mixes two effects — (1) cladding's *spec-as-contract* mechanism (durable, schema-enforced, multi-host), and (2) the general "*more-specific prompt produces more-specific output*" effect, since the cladding-on prompt carries the AC text into the prompt body while the cladding-off prompt is open-ended. Both contributions are real, but only #1 is uniquely cladding, and the benchmark does not isolate them. The four areas where cladding *uniquely* wins — persistence, automatic drift detection, cross-host parity, and audit trail — are independent of the prompt-specificity effect.
