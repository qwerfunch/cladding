# v0.4.0 Consistency Benchmark — cladding-on vs vibe coding

> Measured 2026-05-28 against cladding v0.4.0 release. Six-phase benchmark on isolated `/tmp/clad-bench/` workspace: install + init-scenario matrix + trap gauntlet + consistency thesis + dev cycle + cladding-on/off comparison. Twelve host-AI calls total across Claude Code 2.1.152 and Gemini CLI 0.42.0. **No API keys** were set; `clad init`'s internal LLM dispatcher fell to deterministic fallback, while the host AIs used their own credentials for the slash-command path.

## TL;DR

| Metric | Result | Confidence |
|---|---|---|
| Consistency improvement (cladding-on vs cladding-off, same task ×2) | **60.3%** (443→176 line diff) | high, with caveat below |
| LOC reduction | **52%** (282→135 LOC avg) | high |
| Drift detection in dev cycle (intentional inject) | **100%** (2/2) | high |
| Trap detection (7 deliberate violations) | **4 clean detections + 1 schema-time** (5/7) | high |
| Deterministic CLI byte-consistency | **0 diff** across 4 same-input runs | proven |
| AI inherent non-determinism (Gemini, same prompt ×2) | **79 line diff** | cladding cannot suppress this |

**Headline caveat**: the 60% consistency gain mixes two effects:
1. Cladding's *spec-as-contract* mechanism (durable, schema-enforced, multi-host)
2. The general "*more-specific prompt produces more-specific output*" effect — the cladding-on prompt carries the AC text into the prompt body, while the cladding-off prompt is open-ended

Both contributions are real, but only #1 is uniquely cladding. The benchmark does not isolate them. The four areas where cladding *uniquely* wins are listed under [Where cladding uniquely wins](#where-cladding-uniquely-wins).

## Methodology

Six phases on `/tmp/clad-bench/`:

| Phase | What | Runs |
|---|---|---|
| 0 | `npm pack` + isolated install + verify `mcpServers` shipping | 1 |
| 1 | Init-scenario matrix across direct CLI / Claude `-p` / Gemini `-p` | 9 |
| 2 | Trap gauntlet — inject 7 deliberate violations, observe detection | 7 |
| 3 | **Consistency thesis** — same intent through 6 paths, pairwise diff | 6 |
| 4 | Dev cycle — 5 iterations adding features, modifying ACs, injecting drift | 5 |
| 5 | **Cladding-on vs cladding-off** — same task twice on both paths | 4 |

Total host-AI calls: 12 (8 Claude + 4 Gemini). Estimated cost: $0.30–$0.60 across both providers.

| Run | Host | Files | Lines | Layers | Caps | Auto-created Features |

| s2-claude | Claude `-p` | 9 | 294 | **6** | **8** | 0 |

**Observation**: the two hosts enrich differently.
- **Claude `-p`** subprocess: inner `clad init` runs under the deterministic fallback (the subprocess does not expose MCP sampling back to the parent Claude Code session). Claude's enrichment shows up as *post-init capability/layer edits*, not as auto-created features.
- **Gemini `-p`** + extension: Gemini auto-discovers cladding's MCP server through the extension manifest. Gemini AI invokes `clad_create_feature` and `read_mcp_resource(cladding://spec)` directly during the same call. Hence the autonomous feature creation (s2-gemini: 5 features; s3-gemini: 2 features).

## Phase 2 — Trap gauntlet (7 deliberate violations)

| Trap | Injection | Detector / Result |
|---|---|---|
| **T-1** | AC body uses `description:` instead of `text:` | ✅ `clad sync` schema reject (instance.features[0].acceptance_criteria[0]: is not allowed to have the additional property "description") |
| **T-2** | Feature `modules:` includes a non-existent file path | ✅ `[MISSING_IMPLEMENTATION] src/auth/FAKE-MISSING.ts — feature F-xxx declares module ... but the file does not exist` |
| **T-3** | AC `test_refs:` points to a non-existent test file | ⚠️ **gap** — no detector catches this; `test_refs` is informational only |
| **T-4** | Modify a module body without updating the AC text | (skipped — would require Unit-tests stage runtime + AC↔code semantic compare) |
| **T-5** | Source code violates `forbidden_imports` in `spec/architecture.yaml` | ✅ `[ARCHITECTURE_FROM_SPEC] src/api/server.ts — imports from '../ledger/store.js' which crosses into the 'ledger' layer — forbids imports from 'api' to 'ledger'` |
| **T-6** | Hardcoded `API_KEY = "sk-..."` in source | ⚠️ noisy — `clad check Secret` requires `.secretlintrc` in the target project; when missing, it surfaces an *infra error* rather than detecting the literal secret |
| **T-7** | Capability `features: [F-NONEXIST]` (orphan reference) | ✅ `[CAPABILITIES_FEATURE_MAPPING] spec/capabilities.yaml — capability "card-authorization" references feature F-DOESNTEXIST which does not exist` |

**Detection rate**: 4/7 clean + 1 schema-time = **5/7 = 71%**. The two non-detections are a real gap (T-3) and an infra dependency (T-6).

The v0.4.0 F4 fix (finding-detail surfacing in `clad check`) is visible throughout: every detected trap reports `[DETECTOR_NAME] path — message` inline, with no need to grep `.cladding/events.log.jsonl`.

## Phase 4 — Dev cycle (5 iterations)

Workspace = copy of `s3-direct` (`existing-adoption`, 4 layers).

| Iter | Action | `clad sync` | `clad check Drift` finding |
|---|---|---|---|
| 1 | Author hash-based feature F-α (modules:2, ACs:2, test_refs) | ✓ 1 valid | — |
| 2 | Author hash-based feature F-β (separate layer) | ✓ 2 valid | — |
| 3 | Modify F-α AC-001 body (deliberately diverging from code) | ✓ 2 valid | **bonus: `[AC_DRIFT] F-α.AC-002 EARS: ears='unwanted' requires condition starting with 'if' — empty`** |
| 4 | Update `src/auth/authorize.ts` to match new AC | ✓ 2 valid | (cleared) |
| 5 | Drift inject: change F-β `modules` to a nonexistent path | ✓ 2 valid | **`[MISSING_IMPLEMENTATION] src/billing/NONEXISTENT.ts`** |
|   | Revert | ✓ 2 valid | (cleared) |

Two observations:
1. `clad sync` only enforces *schema*. All five iterations pass.
2. `clad check Drift` enforces *spec ↔ code* and *EARS rigour*. Iteration 3 surfaced a **bonus AC_DRIFT** finding (the AC had `ears: unwanted` but no `condition` starting with `if`) that I hadn't intended to inject — cladding caught a real structural violation, not just my staged ones.

## Phase 5 — Cladding-on vs cladding-off

Same task on both paths, twice each: *"TypeScript HMAC-SHA256 webhook signature validation module + Vitest tests"*.

| Path | Setup | Prompt |
|---|---|---|
| **Cladding-off** (vibe coding) | empty dir | open-ended task description |
| **Cladding-on** (spec-anchored) | `clad init` → hash-based feature shard with 2 ACs | "Implement F-xxxxxx — must satisfy AC-001 and AC-002 exactly as their text describes" |

### Outputs

| Run | Files | Total TS LOC |
|---|---|---|
| off-1 | 2 | 212 |
| off-2 | 2 | 351 |
| on-1 | 2 | 115 |
| on-2 | 2 | 155 |

### Self-consistency (same prompt, same path, twice)

| Path | Δ |
|---|---|
| Vibe coding (off-1 ↔ off-2) | **443 lines** |
| Spec-anchored (on-1 ↔ on-2) | **176 lines** |

→ **cladding-on is 60.3% more consistent than cladding-off.**

### Secondary effects

1. **LOC reduction**: off averages 282 LOC, on averages 135 LOC. The AC text constrains scope, so the implementation stays focused. **52% less code.**
2. **Maintainability**: cladding-on results carry their intent in `spec/features/webhook-hmac-*.yaml` — a future session can reconstruct the goal from the spec. Cladding-off results have only the code; intent reconstruction requires reverse-engineering.
3. **Verifiability**: only cladding-on runs can be checked with `clad check` for spec ↔ code consistency.

## Honest caveats

### 1. The 60% number is partly confounded

Compare the two prompts:
- **Off**: *"Write a TypeScript module src/webhook.ts that validates HMAC-SHA256 signatures... Also write tests..."* (open scope)
- **On**: *"Implement F-xxxxxx — must satisfy AC-001 and AC-002 **exactly as their text describes**"* (constrained scope, with two AC bullets carried in)

A control study with matched information density (same AC text in-prompt, no cladding pipeline) would isolate cladding's *process effect* from the general *detailed-prompt effect*. This benchmark does not run that control.

The 60% gain is real; the *fraction attributable purely to cladding's mechanism* is a strict subset of it.

### 2. AI inherent non-determinism is unchanged

Phase 3 Δ_EF = 79: Gemini, with cladding's MCP wire, still diverges across same-prompt runs by 79 lines. Cladding enforces *schema*; the *content* is still produced by an AI that has its own variance. Cladding does not, and cannot, make AI deterministic.

### 3. There is real overhead

- Plugin/extension install + `clad setup`
- Learning the EARS AC structure
- Authoring spec shards (or having the AI do it, which adds round-trip)
- Maintaining `AGENTS.md` / `CLAUDE.md` synced

For one-shot throwaway scripts, the overhead exceeds the benefit.

## Where cladding uniquely wins

Independent of the "detailed prompt" effect, the benchmark surfaces four areas where cladding contributes value that an in-prompt spec cannot replicate:

| Property | Why it matters | Phase that demonstrates it |
|---|---|---|
| **Persistence** | `spec/features/<slug>-<hash>.yaml` survives session boundaries. A new AI session six months later can reconstruct intent from the spec, not just the code. | Phase 4 — every iter leaves a durable record |
| **Automatic drift detection** | `clad check` surfaces spec↔code violations without human intervention. Bonus finding (AC_DRIFT) shows it goes beyond what was deliberately staged. | Phase 4 iter 3 + iter 5 |
| **Cross-host parity** | The same spec is consumed identically by Claude Code, Codex CLI, Gemini CLI, and Cursor — all four hosts wire cladding as their MCP server. | Phase 1 (host-driven runs) |
| **Audit trail** | `.cladding/events.log.jsonl` and `.cladding/audit.log.jsonl` record what was checked when, by whom. Essential for regulated/enterprise contexts. | Phase 4 (`clad doctor` consumes these) |

A solo throwaway prototype gains little from these four. A team project, a year-long product, or a regulated codebase gains a lot.

## Where cladding does not (yet) help

| Limit | Detail | Issue |
|---|---|---|
| `test_refs` missing | AC may reference a nonexistent test file with no detector flag | F-A (medium) |
| Secret detection setup | `clad check Secret` requires `.secretlintrc` in the target project. Missing config emits a noisy infra error rather than skipping cleanly | F-B (medium) |
| Subprocess MCP bridging | `claude -p` does not bridge MCP sampling from a subprocess `clad init` back to the parent Claude session — that path falls to deterministic fallback | F-C (low) |
| AI variance | Cladding's schema enforces structure but cannot make AI output deterministic. Phase 3 Δ_EF=79 quantifies the floor | F-D (info, not a fixable cladding bug) |

## Cost-benefit by scenario

| Scenario | Recommendation |
|---|---|
| Solo, single-session throwaway | Cladding overhead exceeds benefit |
| Solo, 1–3 month side project | Modest benefit (drift detection + intent persistence) |
| Multi-developer team | **Strong benefit** (hash IDs avoid conflicts, audit trail enables review) |
| Long-lived product (1+ years) | **Strong benefit** (intent reconstruction from spec, not from archaeology) |
| Enterprise / regulated domain | **Highest benefit** (governance + audit are uniquely valuable) |

## Reproducibility

The raw benchmark can be re-run from a clean macOS / Linux system with `node 20+`, `gh`, and the cladding repo cloned locally. Outline:

```sh
# inside the cladding repo
npm pack
mkdir -p /tmp/clad-bench/global
mv cladding-*.tgz /tmp/clad-bench/
npm install -g --prefix /tmp/clad-bench/global /tmp/clad-bench/cladding-*.tgz
export CLAD=/tmp/clad-bench/global/bin/clad

# Phase 1.A — direct CLI
for s in s1 s2 s3 s4 s5; do mkdir -p /tmp/clad-bench/$s-direct; done
# (pre-seed s3-direct with 12 TS files in src/{api,auth,billing,ledger}/ + tests/, package.json, README.md)
# (pre-seed s5-direct with TS + Python source files, pyproject.toml, README.md)
(cd /tmp/clad-bench/s1-direct && $CLAD init "AI 코드 리뷰 SaaS")
(cd /tmp/clad-bench/s2-direct && $CLAD init "B2B 결제 SaaS — Stripe + Toss + 정산")
# … etc

# Phase 5 — cladding-off vs cladding-on
mkdir -p /tmp/clad-bench/p5-off-{1,2} /tmp/clad-bench/p5-on-{1,2}
TASK="Write a TypeScript module src/webhook.ts that validates HMAC-SHA256 signatures on incoming webhook payloads. Also write tests in tests/webhook.test.ts using vitest."
(cd /tmp/clad-bench/p5-off-1 && claude -p "$TASK" --dangerously-skip-permissions)
(cd /tmp/clad-bench/p5-off-2 && claude -p "$TASK" --dangerously-skip-permissions)
# for p5-on-{1,2}: run `clad init` first, author a feature shard, then prompt Claude to implement F-<hash>
# compare with `diff` or a line-counter
```

The full per-phase log and artifact snapshot is at `/tmp/clad-bench/` while the workspace exists (recommended retention: 1 week post-publication).

## Issues filed

- **F-A** — `test_refs` orphan-test detection gap (medium)
- **F-B** — Secret stage's secretlint-config hard dependency (medium)
- **F-C** — Subprocess Claude `-p` doesn't propagate MCP sampling (low)
- **F-D** — AI variance remains; cladding's domain ends at the schema boundary (info)

## Takeaway

cladding measurably helps when **persistence, automatic drift detection, multi-host parity, or audit** are valued. It does not make AI deterministic, and the 60% consistency headline mixes the cladding-specific effect with the general "more specific prompt → more specific output" effect. For teams, long-lived products, and regulated contexts the trade-off lands strongly in cladding's favour; for one-shot prototypes the overhead exceeds the benefit.

**Slogan check**: *Ending vibe coding* is supported here — but the "ending" is closer to *constraining* than *eliminating*. The schema, audit, and detection layers are real; the AI underneath is still an AI.
