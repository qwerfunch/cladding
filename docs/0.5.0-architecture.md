# cladding 0.5.0 — work/drive transaction architecture

Tier: B · Source: hand-authored design doc · Refresh authority: maintainer

This file captures the 0.5.0 vision that the 0.4.x patch series builds toward. It is the meta-spec for the `execute_work` / `execute_drive` MCP tools and the four-layer defense around them. The Tier A feature shards (`F-89406c`, `F-d23cd4`, `F-ca18ea`, `F-bb3c9f`) carry the acceptance criteria; this doc carries the **why** and the **shape** that ties them together.

## Why 0.5.0 — the gap 0.4.x closes

cladding's README promises "spec ↔ code ↔ tests run as a single cycle" and "auto-blocked on every commit". Through 0.4.0 the *infrastructure* (13-stage gate, 27 detectors, 5 personas, MCP server, anti-self-cert) was real but the *automation that fires it on actual AI work* was not. There were no git hooks installed by `clad init`, `clad drive` mutated only an in-memory `done` set without writing back to `spec/features/*.yaml`, and `clad work` was a stub that printed a message and exited.

The 0.4.x series lands the missing automation **without making cladding host-specific**. Watch-daemon options (chokidar) were considered and rejected — they over-reach (catch hand-edits the harness has no business policing), have no transaction boundary, and lose intent. Host-specific hook adapters (Claude Code `hooks.json`, Cursor `.cursor/hooks.json`, Codex Automations, Gemini lifecycle hooks) were considered and demoted to Tier-2 enhancements — the form differs across all four hosts and they leave Gemini effectively unsupported.

**The 0.5.0 model: AI host explicitly enters a cladding transaction via MCP, cladding wraps the work in scope-aware iron law, AI host explicitly completes it.** MCP transport is the only piece that is genuinely host-agnostic in 2026.

## Two transaction units

- **`enter_work` / `complete_work` / `abandon_work`** — atomic, single-feature transaction. Bounded by the F-id supplied. Scope-aware iron law (drift `--scope` from F-bb3c9f, L1 gates, reviewer). Used for "fix X", "refactor Y", "add Z" — anything atomic.
- **`execute_drive(scenarioId | intent)`** — bundled, scenario-unit transaction. The orchestrator persona decomposes the scope into a work sequence and dispatches the underlying `enter_work` calls. Used for "결제 모듈 추가", "refactor the spec layer", "rewrite the onboarding flow" — work that spans several user-visible features.

The boundary is the same scenario / feature dichotomy the spec already encodes. `drive = scenario unit`, `work = feature unit`. The previously-mostly-decorative `spec/scenarios/*.yaml` files become the live transaction anchor.

## Four-layer defense (Layers A → D)

A pure MCP-transaction model would depend 100% on the host AI calling `enter_work` before any Edit/Write. AI self-discipline is fragile (cladding's own threads have caught this failure mode). The 0.5.0 design layers four defenses, ordered by host coverage:

- **Layer A — AGENTS.md / CLAUDE.md trigger guidance** (already landed in F-8880ee, 0.4.1). Host AI reads "you MUST call enter_work before the first code-edit tool" from project memory.
- **Layer B — MCP tool description compulsion**. Each tool's `description` field carries the same MUST-clause; prompt-engineering picks it up alongside Layer A. Host-agnostic — all four hosts surface tool descriptions to their model.
- **Layer C — host-specific hook adapter** (opt-in enhancement, Claude Code first in 0.4.7). `PreToolUse(Edit|Write)` checks the active-work registry; deny + alert when there's no open transaction. Strongest defense, but limited to hosts that expose the right hook.
- **Layer D — post-hoc unmapped-change scan**. Every Edit/Write that occurred between `enter_work` and `complete_work` is recorded in `.cladding/events.log.jsonl`; on the next turn the orchestrator persona compares against the work scope and reports unmapped changes. Catches what slipped past A/B and reaches every host.

Even with Layer C disabled (e.g. on Gemini, which has no equivalent of `PreToolUse`), the A+B+D triad guards SSoT correctness, just with a slightly larger feedback delay.

## Persona dispatch — option 1 (host AI is the LLM)

When `enter_work` returns the specialists persona prompt and the scoped module list, the host AI adopts that persona for the next turn. **cladding never dispatches an LLM call itself.** This keeps the harness host-agnostic (no API-key plumbing, no MCP-sampling dependency that is only stable on Claude Code) and zero-cost to maintain.

The cost: cladding cannot enforce persona-correctness — the host AI may ignore the prompt. Mitigations are the same Layer-A / Layer-B compulsion text, plus the existing `ReviewerIdentityCollisionError` runtime barrier (specialist → reviewer identity must differ; already implemented in `src/drive/agent.ts:58-94`).

A future 0.5.x option: use MCP `sampling/createMessage` to have cladding-server explicitly invoke the host's LLM with the persona prompt as the system message. Available on Claude Code today, fragile elsewhere — deferred.

## Implicit close

`complete_work` is the explicit close. cladding cannot rely on the host AI to always call it (the user may abandon the turn, the host may crash, the LLM may forget). Three implicit-close triggers, in priority order:

1. **Host Stop hook** (when available — Claude Code 0.4.7) — turn ends → close any open work for the session.
2. **Next-prompt-different-feature** — the orchestrator persona detects a switched featureId on the next `enter_work` and closes the prior transaction.
3. **Wall-clock timeout** — default 10 minutes, settable via `spec.yaml::project.ai_hints.work_timeout_seconds`. Fallback when both (1) and (2) miss.

Implicit close **never rewrites status** (`in_progress` stays `in_progress`); rollback / scratch-isolation is a 0.5.x candidate. The Layer-D event log carries the `work_timed_out` record so the next session can resume or explicitly abandon.
